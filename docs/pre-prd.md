# pre-prd Pre-PRD

- **한 줄 요약:** 아이디어를 짧게 던지면, 쉬운 질문으로 이끌어 요구사항을 확립하고 일관된 Pre-PRD 한 장으로 정리해 주는 로컬 웹 도구
- **모호도:** 문제 0.9 · 사람 0.8 · 장면 0.7 · 핵심 0.9 · 경계 0.8 · 확인 0.7 (평균 0.80)
- **작성일:** 2026-11-21
- **상태:** MVP 요구사항 확정 전 초안

## 1. 문제

- 아이디어는 있는데 "무엇을 만들지"가 정리되지 않은 채 개발자에게 넘어간다.
- 표준 PRD 템플릿은 전문 용어(기능, 범위, KPI)를 요구해 비전문가가 채우기 어렵다.
- 그래서 개발자가 착수 후에 요구사항을 다시 캐묻는 비용이 생긴다.
- 현재 해결 방법: 대화나 메모로 즉흥적으로 정리 → 매번 형태가 다르다.

## 2. 사람

- **본인(개발자):** 사이드 프로젝트나 외주를 시작하기 전에 생각을 정리한다.
- **PM/기획자(비전문가 포함):** 개발자에게 넘기기 전에 요구사항을 확립한다.
- 공통점: 전문 PRD 작성자가 아니다. 무엇을 원하는지 아직 명확하지 않다.

## 3. 장면

1. "동네 중고거래 앱 만들고 싶어"라고 한두 줄 입력한다.
2. 웹 화면에 질문이 하나씩 뜨고, 선택지를 고르거나(AskUserQuestion 방식) 직접 적는다.
3. 단계마다 진행률과 모호도 점수, 아직 빈 항목이 보인다. 점수가 기준을 넘으면 다음 단계로 간다.
4. 6단계가 끝나면 Pre-PRD 미리보기가 뜨고, `pre-prd.md`로 저장된다.
5. 중간에 닫아도 다음에 이어서 진행할 수 있다.

## 4. 핵심

- **이것만 되면 성공:** 짧은 입력 → 단계별 질문 → 항상 같은 구조의 Pre-PRD 한 장.
- **인터뷰 단계 (= 문서 섹션):** 문제 → 사람 → 장면 → 핵심 → 경계 → 확인
- **모호도 판정:** 단계마다 "채워져야 할 사실" 2~4개를 정해 두고, LLM이 각 항목을 0~1로 채점한다. 평균 0.8 이상이면 통과하고, 점수 근거를 화면에 보여 준다.
- **성공 판단 기준:** 개발자가 Pre-PRD만 읽고 "무엇을, 누구에게, 왜, 어디까지" 만드는지 되묻지 않는다.

**단계별 체크 항목** (항목마다 0~1점, 평균 0.8 이상이면 통과)

| 단계 | 채워져야 할 사실 |
|---|---|
| 1. 문제 | ① 누가 겪는 불편인가 ② 지금은 어떻게 해결하고 있나 ③ 그 방법이 왜 불편한가 |
| 2. 사람 | ① 처음 쓸 사람을 구체적으로 묘사 ② 언제·어디서·어떤 기기로 쓰나 ③ 사람 유형이 여럿이면 누가 먼저인가 |
| 3. 장면 | ① 시작부터 끝까지 흐름 1개 이상 ② 끝났을 때 사용자가 얻는 것 ③ 막히거나 실패하는 순간 |
| 4. 핵심 | ① 딱 하나만 된다면 그게 무엇인가 ② 성공했다고 눈으로 확인할 기준 |
| 5. 경계 | ① 이번에 안 할 것 1개 이상 ② 제약(예산·일정·기기·플랫폼) |
| 6. 확인 | ① 단계끼리 모순이 없다 ② 0.6점 미만 항목이 없다 |

**문서 종류** — 시작할 때 고른다. 위 표는 **새 아이디어**의 단계다. 이미 있는 서비스를 바꾸는 **유지보수** 요청은 아래 단계(= 섹션, 제목은 질문형)로 묻는다.

| 단계 | 채워져야 할 사실 |
|---|---|
| 1. 무엇이 바뀌나요? | ① 지금까지 어떻게 동작하나 ② 앞으로 어떻게 바뀌나 ③ 바뀌는 화면·기능이 어디인가 |
| 2. 왜 이 기능이 필요한가요? | ① 지금 어떤 문제가 생기고 있나 ② 안 바꾸면 무엇이 계속 손해인가 |
| 3. 요청자는 무엇이 필요한가요? | ① 누가 요청했나 ② 요청자에게 꼭 필요한 것 |
| 4. 고객은 어떤 점이 좋아지나요? | ① 영향받는 고객은 누구인가 ② 고객이 체감할 변화 |
| 5. 이번에 안 하는 것 | ① 이번에 안 할 것 1개 이상 ② 제약(일정·영향 범위) |
| 6. 잘 됐는지 어떻게 아나요? | ① 눈으로 확인할 성공 기준 ② 확인 방법·시점 |
| 7. 확인 | 새 아이디어와 같음 |

유지보수 문서도 끝에 확인된 결정 · 남은 질문 · 부록을 붙인다.

**질문 규칙**
- 한 번에 질문 1개를 내고, 선택지 2~4개와 직접 입력을 함께 준다. 선택지에는 항상 "잘 모르겠어요"를 넣고, 이걸 고르면 그 항목은 "남은 질문"으로 간다.
- 단계당 최대 4문항까지 묻는다. 넘겨도 통과하지 못하면 미달 항목을 "남은 질문"으로 넘기고 다음 단계로 간다. 전체 15~20문항, 10~15분이 목표다.
- 확인 단계는 단계끼리 모순되는 부분과 0.6점 미만 항목만 다시 묻는다(최대 3문항, 새 주제 없음). 그다음 미리보기를 보여 주고 사용자가 "확정" 또는 "이 부분 수정"을 고른다.
- 언어는 한국어 전용이다.

## 5. 경계

**MVP에서 하지 않을 것**
- 배포, 로그인, 다중 사용자 협업(PM↔개발자 공유)
- 표준 PRD, 기능명세, ERD 등 전문 산출물 (필요하면 이후 `project-docs-gen`에 연결)
- GitHub 레포·이슈 자동 생성
- Claude API 키 방식 (구독 기반 로컬 실행만)

**제약**
- 로컬 전용: `localhost` 웹 + 내 Claude 구독(로컬 Claude Code 로그인)
- 스택: Next.js(TypeScript) + Claude Agent SDK
- 저장: 프로젝트별 로컬 폴더 (`session.json` 중간 상태, `pre-prd.md` 결과)

## 6. 확인된 결정

| 결정 | 이유 |
|---|---|
| 표준 PRD가 아니라 Pre-PRD | 대상이 전문가가 아니라 요구사항이 정리되지 않은 사람이기 때문 |
| 단계 = 섹션 1:1 | 결과물 형태를 항상 같게 유지 |
| 웹에서 선택지 기반 대화 | 비전문가도 답하기 쉽다. 터미널 의존을 없앤다 |
| 구독 기반 로컬 실행 | MVP라 API 키, 비용 관리, 배포를 피한다 |
| 체크 항목 + LLM 채점 | 자유 판단보다 일관성이 높고 근거를 보여 줄 수 있다 |
| 로컬 파일 저장 | DB 없이 이어하기와 결과 공유가 가능하다 |

## 7. 남은 질문

1. **구독 인증 실측 필요 (결정: Agent SDK + 구독):** SDK는 Claude Code를 내장하고, 인증 우선순위의 마지막이 `/login` 구독 자격증명이다. 다만 SDK 문서가 이를 명시하지 않으므로 `ANTHROPIC_API_KEY` 없이 최소 `query()`를 돌려 확인한다. 안 되면 `claude setup-token` → `CLAUDE_CODE_OAUTH_TOKEN`을 쓴다. 약관상 금지는 "제3자에게 claude.ai 로그인을 제공하는 것"이므로 1인 localhost 전용으로 유지하고, 공유하거나 배포할 때는 API 키로 전환한다. 선택지 UI는 `canUseTool`이 `AskUserQuestion` 호출을 가로채 웹 화면에 띄우는 방식으로 지원된다. 한 번에 1~4문항, 선택지 2~4개이고, 권한 모드는 `default`를 쓴다(`dontAsk`·`bypassPermissions`는 이 콜백이 동작하지 않는다).
2. **(나중) 스킬 재사용:** 단계별 프롬프트를 Claude Code에서도 `/pre-prd`로 쓸 수 있게 할지. MVP 범위 밖이다.
